# 更新检查设计说明

状态：v1（源码安装、Web 工作台与实时看板）。本文说明版本与渠道模型、检查流程、失败行为、接口契约和已知边界。

## 目标与不做的事

目标是让用户打开软件时看到「有没有新版本、新版本里有什么、我该怎么升级」。

**不做**：自动下载、自动替换代码、自动重启、后台常驻更新服务。本项目是交易辅助工具，更新动作本身不能成为运行期的不确定因素。

## 版本与渠道模型

**渠道是安装版本 tag 的属性，不是运行环境的属性。** 镜像 `ghcr.io/luqtest/big-a-chovy:v0.7.0` 属于正式版渠道——它的升级路径就是「0.7.1 发布了 → 换新镜像」；`v0.6.0-docker.2` 才属于容器版渠道。如果把「是否跑在容器里」当成渠道，所有用正式镜像的用户都永远收不到更新提示。

| tag 形态 | 渠道 | 说明 |
|---|---|---|
| `vX.Y.Z` | `stable` | 正式版 |
| `vX.Y.Z-preview.N` | `preview` | 预览版 |
| `vX.Y.Z-docker.N` | `docker` | 容器版 |

仓库根 `VERSION` 只保存**共同的基础版本**（当前 `0.7.0`）。渠道与渠道序号由发布 tag 提供；`v0.6.0-docker.2` 与 `v0.6.0-preview.2` 来自同一源码提交（见 CHANGELOG），是同一基础版本的两种打包形态。

不认识的 tag 形态（如 `v0.7.0-rc.1`）解析为「无法比较」，**不猜成正式版**——猜错的代价是给用户一个错误的升级建议。

本地版本解析顺序：

1. `A_SHARE_VERSION`（Docker 构建按 tag 烤入）——完整版本，含渠道；
2. 否则读 `VERSION` 作基础版本，渠道按 `A_SHARE_CHANNEL`（默认 `stable`，取值写错时退回 `stable`，这是最保守口径）。

## 检查流程

1. 请求 `GET /repos/LuQTest/Big-A-chovy/releases?per_page=30`。
2. 按 tag 后缀筛出**本渠道**的候选版本。
3. 只在同渠道内取最大版本，与之比较。

**为什么查 Releases 列表而不是 `/releases/latest`**：后者按 GitHub 定义只返回非预发布、非草稿的 Release，预览版一旦按发布方案标成 prerelease 就会被它整体漏掉。当前仓库有 3 个正式 Release（`v0.7.0`、`v0.6.1`、`v0.6.0`），`-preview.N` / `-docker.N` 还只有 git tag，一旦按方案补发预览 Release，`/releases/latest` 就会开始漏。

正式版渠道额外要求上游没有标 `prerelease`：宁可漏一次提示，也不要把预发布物当成正式版推给只跟正式版的安装。预览版和容器版本身就是预发布物，该布尔位不参与判定。

## 比较规则

- 同渠道内先比基础版本 `X.Y.Z`，再比渠道序号 `N`。
- **跨渠道一律不算更新**。这条是硬约定，测试逐组合锁住（`0.9.0-docker.1` 相对 `v0.6.1`、`0.9.0-preview.1` 相对 `0.9.0-docker.1` 等）。
- 本机版本不低于候选版本时不出提示。

## 失败、缓存与阻塞

- **静默失败**：离线、`403/429` 限流、证书问题、返回体畸形或结构异常，都只体现在返回值的 `status` / `detail` 里；不抛出、不打印、不弹窗，软件照常使用。
- **24 小时缓存**：缓存写在运行状态目录（跟随 `A_SHARE_STATE_DIR`），命中时不联网。缓存按渠道和本机基础版本分别生效，换了渠道或版本会重新查。
- **失败沿用上次好结果**：上游不可用期间保留上一次查到的版本与正文，并把失败原因附在 `detail` 里，同时顺延下次尝试，避免上游故障期间反复打接口。
- **绝不阻塞请求**：接口只读内存或磁盘快照；首次检查在后台线程里跑。缓存新鲜时连线程都不起，避免每次轮询空转、`checking` 标志闪烁。
- 超时 4 秒；响应体读取上限 1 MiB；正文截断 4000 字符。

## 接口契约

`GET /api/update`，可带 `?force=1` 跳过缓存重新检查。关键字段：

| 字段 | 含义 |
|---|---|
| `status` | `ok` / `checking` / `unavailable` / `disabled` |
| `update_available` | 同渠道内是否存在更新 |
| `local_version` / `latest_version` | 本机与最新版本（不含 `v` 前缀） |
| `channel` / `channel_label` | 渠道与中文名 |
| `release_notes` / `release_url` / `published_at` | 更新内容与 Release 页地址 |
| `install_hint` / `image_ref` | 升级命令与对应镜像引用 |
| `detail` | 失败原因或「本渠道暂无 Release 记录」 |
| `checking` | 是否仍有后台检查在跑 |

端点挂在看板的 handler 上，工作台 handler 继承它，两个入口共用同一份实现。

## 前端

渲染逻辑在共用层 `shared_static/common.js`，两个页面都只在 HTML 里留一个 `#update-notice` 席位，启动代码由共用层自挂载，避免两个入口各写一份后漂移。

- **非模态、默认折叠**：常态只有一行「本机版本 + 渠道」，有新版才出现蓝色胶囊；更新内容要点开才展开，不遮挡盘中操作。
- **不做 Markdown→HTML**：Release 正文是第三方文本，一律 `esc()` 转义后按纯文本渲染，只把行首的 `-`/`*` 换成项目符号。不引入渲染器，也就不存在需要过滤的标记注入面。
- **链接白名单**：`release_url` 服务端只放行 `https://github.com/` 前缀（并拒绝含空格与控制字符的值），前端再校验一次，`href` 用属性赋值而非拼进 `innerHTML`，并带 `target="_blank" rel="noopener noreferrer"`。

## 升级指令与实际安装方式

指令必须与本机安装方式一致，否则用户照做会失败或得到误导：

| 安装方式 | 提示命令 |
|---|---|
| 源码 clone | `git pull` |
| Compose 引用 GHCR 镜像 | `docker compose pull && docker compose up -d` |
| Compose 本地 `build`（本仓库自带形态） | `git pull && docker compose up -d --build` |
| `docker run` | `docker pull ghcr.io/luqtest/big-a-chovy:v<版本>` |

容器形态用 `A_SHARE_DOCKER_MODE`（`auto` / `image` / `build` / `run`）覆盖，默认 `auto`：读随镜像分发的 `docker-compose.yml`，见到 `image: ghcr.io/...` 判为镜像版，见到 `build:` 判为源码构建版，判不出来退回 `run`，不猜。**本仓库自带的 compose 用 `build:`，此时 `docker compose pull` 无意义，因此不会被提示。**

## 运行状态隔离

检查缓存是运行状态，跟随 `A_SHARE_STATE_DIR`。测试与实跑验证必须定向到临时目录；测试套件另有一条断言，确认缓存不会落在真实脚本目录。

## 发布流程要求

发布新版本时：

1. 先把 `VERSION` 改成新基础版本；
2. CHANGELOG 顶部加入对应条目；
3. 打 tag（`vX.Y.Z` / `-preview.N` / `-docker.N`）；
4. CI 会跑 `tools/validate_version.py --tag <tag>`：**基础版本与渠道分别校验**——tag 的基础版本必须等于 `VERSION`，渠道必须是已知渠道之一。不一致时流水线失败，镜像也不发布。

`tools/validate_consistency.py` 已把同一校验并入工作区对账。

## 已知边界

- **容器版渠道目前没有 Release 记录**：`-docker.N` 只有 git tag。此时接口如实返回「本渠道暂无 Release 记录」，不会谎报「已是最新」。等容器版开始发布 Release 后自动生效。
- **Tkinter GUI（`a_share_screen_gui.py`）未接入**：v1 只覆盖 Web 工作台与实时看板。检查能力的核心已在独立模块里，GUI 接入时复用即可。
- **渠道靠 tag 约定**：维护者把预览版打成 `vX.Y.Z` 就会进入正式版渠道。这是发布规范问题，`validate_version.py` 只能校验形态、无法校验意图。
- 上游公开接口可能变化；GitHub API 未认证请求有 60 次/小时的限额，24 小时缓存下远不到上限。
