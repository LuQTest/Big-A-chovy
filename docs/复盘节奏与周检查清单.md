# 复盘节奏与周检查清单

> 建议节奏：**每个交易周一次（约 5 个交易日），最长不超过 10 个交易日。**
> 本文只讲"怎么检查"，不改任何规则；参数变更走 `选股框架.md` 的验证流程。

## 为什么是 5–10 个交易日

- **下限 5 个交易日**：少于一周的样本量做不出任何结论。框架里待验证项的门槛是 **20 个完整结算样本**才评估转正；一周的数据只够用来发现"操作和运维上的问题"，不够用来证明规则好坏。
- **上限 10 个交易日**：漏筛、上游接口失效、执行纪律漂移会累积成系统性偏差却没人发现。上游数据的稳定性可以量化——本项目在 2026-09 的一周内就连续遇到三次接口失效（行情主路由下线、日 K 主源下线、日 K 备用源被 WAF 拦截），这类问题只有主动检查才会暴露。

**所以 5–10 天这个节奏属于运维检查，不属于参数调优。** 两者分开，是这份清单最重要的前提。

## 周检查清单

### 1. 数据源健康（先做，2 分钟）

```bash
python3 tools/verify_em_webguest.py
python3 daily-stock-analysis/scripts/network_path.py
```

- 前者的结论行应是 `RESULT: required webguest routes usable`；出现 FAIL 要先查清是哪一类问题（限流 / 路径下线 / 拦截，区别见 `docs/东财请求频率与限流.md`）。
- 顺手看本周报告头部的 **`来源：`** 行：如果出现 `新浪日K(可能不复权)`，说明日 K 主源当轮不可用，那一轮的均线口径要打折看，记下来。

### 2. 全天报告扫描

```bash
python3 tools/scan_reports.py --date YYYYMMDD
```

逐日跑一遍，看 5/5、4/5 标的的分布：本周有没有"当天出现但一直没进池"的、有没有"进池后次日就破位"的。空结果先排查解析问题，不要直接当成"没有候选"。

### 3. 单股回看

```bash
python3 tools/track_stock.py <代码> --date YYYYMMDD
```

对本周实际关注过的标的，回看它一天里的状态变化（进入哪个池、什么相位、有没有衰减）。比只看最终报告更能看出"什么时候该进、什么时候已经晚了"。

### 4. 执行对照（最有效的一条）

把本周的**实际操作**与**当时报告的建议**逐笔对照，重点只看三类偏差：

| 偏差类型 | 怎么判断 |
|---|---|
| 追高 | 买入价处于当日区间的高位（报告里的「区间分位」列可直接看） |
| 在追高禁区买入 | 买入价高于当日报告写的追高禁区 |
| 在低吸区外买入 | 买入价没有落在报告给出的低吸区内 |

这一条是整份清单里收益最高的：规则再好，执行偏差都会把结果吃掉；而执行是唯一完全可控的变量。

### 5. 记录

结论写进**本地**决策记录（`决策记录/YYYYMMDD.md`）。仓库里只保留方法论，不提交任何持仓、成交价、金额或个人决策记录（见 README 的隐私与社区规范）。

## 明确不要做的事

1. **不要用一周的盈亏去改门槛。** 一周的涨跌不能证明规则好坏——大盘同期涨跌往往占了大头。参数变更必须走框架流程：影子采样 → T+1 结算 → 达到样本门槛后评估转正。
2. **不要只改数字不留记录。** 框架规定参数只在 `tools/rule_config.py` 与框架参数总表维护，变更要写明原因、来源、状态与适用仓位；否则不同时期的样本不可比。
3. **不要把复盘写成预测。** 输出规则结果与证据，不写"我觉得下周会怎样"。
4. **不要在仓库里讨论个股买卖。** 社区只讨论代码、数据、测试、文档和本地运行问题。

## 一周复盘产出什么

一份写进本地决策记录的短记录，四行就够：

```markdown
## 周复盘 YYYYMMDD–YYYYMMDD
- 数据源：本周是否出现降级/失效，记录发生的日期与降级来源
- 漏筛/误筛：本周值得记录的个案与原因（数据缺失 / 信号衰减 / 解析异常）
- 执行偏差：追高 / 禁区 / 低吸区外，各有几笔，分别是什么情况
- 待办：下周要盯的数据项或规则验证进度（不改参数，只登记待验证）
```
